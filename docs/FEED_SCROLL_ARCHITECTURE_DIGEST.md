# Feed + Reply + Scroll Architecture Digest
### How top Nostr clients & big social apps do it — applied to a Flutter (Riverpod + sqflite) Nostr client with Android scroll jank / "stuck after a while"

Sources: GitHub repos & PRs (Amethyst, Damus/nostrdb, rx-nostr, NDK, Primal, applesauce/Nostrudel, Flutter), NIPs, Flutter/Android docs, engineering blogs. All URLs inline.

## 1. FEED LOADING STRATEGY IN NOSTR CLIENTS

### 1.1 Batch fetching: events + engagement + profiles

**The dominant pattern: one event store, one subscription manager, batched REQs keyed by what's visible.**

- **Amethyst** keeps *all* Nostr objects in an in-memory OO graph (`Note`/`User` objects, single instance per id/pubkey, "there will never be two Notes with the same ID"). The repository layer exposes LiveData/Flow per object so UI subscribes to individual notes; "as the user scrolls through Events, the Datasource classes are updated to receive more information about those particular Events." Relay connections are *never closed during app use*; the service layer assembles filters per need. [github.com/vitorpamplona/amethyst](https://github.com/vitorpamplona/amethyst)
  - Filter *assemblers* are pure functions: `MetadataFilterAssembler(setOf(pubkeys))` → `Filter(kinds=[0], authors=pubkeys, limit=pubkeys.size)`. A `FeedMetadataCoordinator` takes the **list of visible notes** and builds ONE metadata filter covering every referenced pubkey. `ReactionsFilterAssembler` does kind-7 for N note ids. [.claude/skills/relay-client SKILL.md](https://laantungir.net/git/laantungir/amethyst/raw/tag/v1.13.1/.claude/skills/relay-client/SKILL.md)
  - Bulk fetches are rate-limited: `MetadataPreloader` + `MetadataRateLimiter` (token bucket) — "I need metadata for 200 pubkeys, but don't melt my CPU or the relay" — chunked into relay-friendly groups. (same source)
  - Subscription dedup: `MutableComposeSubscriptionManager` uses **reference counting** — two screens asking for the same feed share ONE subscription; only the last leaver closes it. (same source)

- **rx-nostr (used by Nostter, many web clients)** has canonical operators for this:
  - `bufferTime(1000) + batch()` — collect REQ packets emitted over 1s and merge filters into one REQ. The canonical example is exactly "get kind-0 of users appearing in the timeline": `profileReq.emit({kinds:[0], authors:[event.pubkey], limit:1})` batched every second, then `latestEach(pubkey)` to keep only newest replaceable. [rx-nostr REQ packet operators](https://penpenpng.github.io/rx-nostr/en/v3/req-packet-operators.html)
  - `chunk()` splits oversized REQs to respect relay `max_filters` (NIP-11). (same source)
  - Real-world usage (Nostter): three backward REQs — `metadataReq`, `eventsReq` (e-tag/q-tag ids), `replaceableEventsReq` (a-tags) — each piped through `bufferTime(1000, null, 10), batch()`, then `tie, uniq(), latestEach(...)`. Relay hints recorded via `createTie()` (`seenOn: Map<eventId, Set<relayUrl>>`) and used to route follow-up fetches. [Nostter MainTimeline.ts](https://github.com/SnowCait/nostter/blob/f91a2f26f4e5922055624ffafb8bdc67d0e16fd6/web/src/lib/timelines/MainTimeline.ts)

- **Primal** cheats (deliberately): all reads go to Primal's proprietary **cache server** over `["REQ", subId, {"cache": ["feed", {...}]}]`. The server ingests from 100+ relays in real time, stores in PostgreSQL, **pre-computes** engagement (replies/reposts/likes/zap sats), follower counts, trending. Response time <100ms. Threads come from `{"cache": ["thread_view", {"event_id": ...}]}`; engagement is batched per page. [primal-caching-service README](https://github.com/PrimalHQ/primal-caching-service), [primal-server](https://github.com/PrimalHQ/primal-server), [SELF_HOSTING_PRIMAL_SERVER.md](https://github.com/silentius-satoshi/ZapTok/blob/main/public/future-implementations/SELF_HOSTING_PRIMAL_SERVER.md). The client never assembles engagement client-side — this is why Primal feels instant. Takeaway for a self-contained client: pre-compute engagement **into sqflite** on ingest, not at render time.

- **NDK (JS) / outbox model**: `OutboxTracker` (LRU 100k entries, 2-min TTL) batches up to 400 users per relay-list fetch; `chooseRelayCombinationForPubkeys` returns `Map<relayUrl, pubkeys[]>` so each relay gets exactly the authors it serves; count=2 relays per author. Publishing: author's write relays + relay hints from e/a tags (≤5) + read relays of p-tagged users (if <5 tags). [NDK OUTBOX-REPORT.md](https://github.com/nostr-dev-kit/ndk/blob/master/core/OUTBOX-REPORT.md)
- **NIP-65 rules**: fetch events FROM a user via their **write** relays; events ABOUT a user (mentions) via their **read** relays; keep lists 2–4 relays; re-publish your kind:10002 alongside your events to indexer relays (purplepag.es, relay.nostr.band). [NIP-65](https://github.com/nostr-protocol/nips/blob/master/65.md), [nip.guide/nips/65](https://www.nip.guide/nips/65)
- Missing kind:10002 (real gap ~3–5% of *active* users): fallback = hardcoded popular relays + e/p-tag relay hints + indexer relays + "track which relays delivered events" (Gossip/rust-nostr/Amethyst all do this). [nostrability/outbox IMPLEMENTATION-GUIDE.md](https://github.com/nostrability/outbox/blob/main/IMPLEMENTATION-GUIDE.md)

**Coracle** differentiator: outbox-model feed construction + relay fallback that "keeps timelines loading even when individual relays go down" + **negentropy-based sync** so refreshes only pull what changed. [OpenSats Coracle](https://opensats.org/projects/coracle)

### 1.2 Pagination, live tails, dedup/merge without re-ordering

- **Cursor = `until` (created_at of oldest visible event), page = `limit`.** NIP-01 filters support `since`/`until`/`limit` natively — this *is* cursor pagination on an immutable-ish sort field. General cursor-pagination literature confirms: paginate on immutable fields (created_at + id tiebreak), never offset, because inserts shift offsets and cause dupes/gaps. [knit.dev pagination stability](https://getknit.dev/blog/how-to-preserve-api-pagination-stability), [brunoscheufler cursor pagination](https://www.brunoscheufler.com/p/2022-01-01-paginating-large-ordered-datasets-with-cursor-based-pagination)
- **rx-nostr Forward vs Backward strategy** is the cleanest formalization:
  - *Forward* (`createRxForwardReq`): one persistent sub (same subId, overwritten), for future events — live tail with `{since: now}`. Use **lazy since/until** (`{since: () => now()}`) so reconnects re-evaluate the timestamp instead of re-requesting a now-stale window.
  - *Backward* (`createRxBackwardReq`): one sub per emit, auto-CLOSE'd on EOSE (or 30s no-event timeout) — for historical pages with `until`. `rxReq.over()` + completion = "all pages' EOSE received". [rx-nostr subscribe-event](https://penpenpng.github.io/rx-nostr/en/v3/subscribe-event.html), [reconnection](https://penpenpng.github.io/rx-nostr/en/v3/reconnection.html)
- **Dedup**: `uniq()` (by event.id, across relays), `tie()` (records `seenOn` relays per id, must run *before* `uniq()`), `latestEach(pubkey)` for replaceables, `latest()` to enforce chronological flow. [rx-nostr event operators](https://penpenpng.github.io/rx-nostr/en/v3/event-packet-operators.html)
- **No-reorder merge**: append historical pages at the bottom; insert live-tail events above a "N new notes" pill (Primal/Twitter pattern) rather than splicing into the visible window — splicing shifts item positions and breaks scroll anchoring (and in Flutter, forces relayout of everything below). Primal does exactly this: "pagination and the new-notes poll". [nostr-swarm primal-shim docs](https://github.com/sovITxyz/nostr-swarm/blob/main/docs/primal-shim.md)
- **REQ queue respecting NIP-11**: relays cap concurrent subs; queue instead of violating. (rx-nostr README, above)

### 1.3 Replies: NIP-10 threading, counts, assembly under incomplete data

- **NIP-10 marked e-tags (preferred)**: `["e", <id>, <relay-url>, "root"|"reply"|"mention", <author-pubkey>]`. Direct reply to root uses a single `"root"` marker (root == reply). Deprecated positional scheme (first e = root, last = reply, middle = mentions) must still be parsed. `p` tags of a reply must include parent author's pubkey + all parent's p-tags (thread notification). Relay hint SHOULD be included; author pubkey SHOULD be 4th element so outbox fetches can find the parent via author's write relays. [NIP-10](https://github.com/nostr-protocol/nips/blob/master/10.md)
- Reference parsers handle the messy reality: nostr-tools `nip10.parse` ([source](https://github.com/nbd-wtf/nostr-tools/blob/master/nip10.ts)), applesauce `interpretThreadTags`/`getNip10References` with symbol-cached per-event memoization ([threading.ts](https://github.com/hzrd149/applesauce/blob/e5a93dc9e8d621137590845e139926638e954312/packages/common/src/helpers/threading.ts)) — *cache the parse result on the event object*, don't re-parse tags per render.
- **Thread assembly client-side**: applesauce pattern — `threadRoot$` / `replyingTo$` observables resolve via `store.event(id)`, and a configured **event loader fetches missing events from relays (using relay hints) on demand**. So the thread view renders what's in the local store and backfills gaps. [applesauce Notes & Threads](https://applesauce.build/features/notes-and-threads.html)
- **Do replies appear in the main feed?** Amethyst's feed projections filter with `isNewThread()` (kind-1 with no e-tags) for the home feed — replies live in their own feeds/threads. [quartz README example](https://laantungir.net/git/laantungir/amethyst/src/branch/main/quartz). Primal's `thread_view` verb returns parent chain + replies + engagement counts server-side. General UX guidance: calculate reply counts from kind-1 events with `#e` pointing at the note; zaps are the strongest quality signal for ranking. [nostr-ux.com content discovery](https://nostr-ux.com/docs/patterns/02-content-discovery)
- **Practical reply counts without NIP-45**: one batched REQ `{kinds:[1], #e: [visible note ids...]}` (backward strategy, EOSE-terminated), count client-side, cache counts in DB keyed by note id. If relays support NIP-45 COUNT, prefer it.

### 1.4 Caching: event stores & schemas

- **nostrdb (Damus)**: LMDB-backed embedded DB; notes stored in a custom flatbuffers-like in-memory format = **zero-copy, O(1) field access**, memory-mapped; design copied from strfry relay. All ingested notes are signature-validated at ingest. Damus's direction: **"local relay model"** — UI only ever queries the local validated DB, never trusts relay responses; this fixes rogue-relay injection, removes async parse-before-render delays ("local subscriptions are notified only after we parse note contents"), halves processing, saves battery; enables negentropy sync. [nostrdb repo](https://github.com/damus-io/nostrdb), [Damus issue #2041 Local Relay Model](https://github.com/damus-io/damus/issues/2041), [Damus 1.6 announcement](https://damus.io/note1p8mzclawd5kxg5rm326vdmlvqzhpwk3ya2g4y7p44t6e669wv6xqf7wfx4)
- **Amethyst/Quartz store layering** (directly cloneable in Flutter):
  `EventStore (SQLite)` → `InterningEventStore` (single in-memory copy per event) → `ObservableEventStore` (flows that auto-update) + `EventCollector` writing ALL inbound events into the store regardless of subscription. Feeds are **projections**: `db.project<Note>(filter).filterItems{...}` + relay subscription bound to collection lifetime (`onStart` subscribe / `onCompletion` unsubscribe, `SharingStarted.WhileSubscribed(5000)`). Periodic NIP-40 sweep every 15 min deletes expired events so DB doesn't grow monotonically. [quartz README](https://laantungir.net/git/laantungir/amethyst/src/branch/main/quartz), [PR #2672](https://github.com/vitorpamplona/amethyst/pull/2672)
- **applesauce (Nostrudel)**: RxJS `EventStore` + `RelayPool` + `createEventLoaderForStore(store, pool)` — any `store.event(id)` read auto-triggers a relay fetch on miss. Nostrudel also supports `CACHE_RELAY` (use a relay as the event cache instead of browser storage) and an `IMAGE_PROXY` to resize profile images server-side. [applesauce.build](https://applesauce.build), [nostrudel repo](https://github.com/hzrd149/nostrudel)
- **Flutter sqflite equivalent schema** (recommended, mirrors the above):
  - `events(id PK, pubkey, kind, created_at, content, tags_json, sig, raw_json, first_seen_at)` with indexes on `(kind, created_at DESC)`, `pubkey`, and a tag index table `event_tags(event_id, tag_name, tag_value)` indexed on `(tag_name, tag_value)` — this is how you serve `#e`/`#p` queries (replies, mentions, reactions) locally.
  - `profiles(pubkey PK, metadata_json, updated_at)`; `relay_lists(pubkey PK, read_json, write_json, updated_at)`; `seen_on(event_id, relay_url)` (the `tie()` table — also your relay-hint source for thread backfill); `engagement(event_id PK, reply_count, reaction_count, repost_count, zap_sats, computed_at)` refreshed by background batch queries.

## 2. SMOOTH SCROLLING ON MOBILE (FLUTTER)

### 2.1 ListView best practices

- **Always `ListView.builder`** (lazy) — the default constructor builds every child eagerly. [Flutter long lists cookbook](https://docs.flutter.dev/cookbook/lists/long-lists), [Flutter perf best practices](https://docs.flutter.dev/perf/best-practices)
- **Fixed extent when possible**: `itemExtent`/`prototypeItem`/`itemExtentBuilder` — "more efficient because the scrolling machinery can use foreknowledge of the children's extent to save work." [ListView API docs](https://api.flutter.dev/flutter/widgets/ListView-class.html). Variable-height lists + big jumps are pathological (Flutter issue #52207: frame times up to 1300ms with 10k variable items + scrollbar jumps) — framework can't shortcut extent computation. Mitigations: fixed-height card variants, or the **`super_sliver_list` package** (caches per-item extents as *estimates*, corrects scroll offset as real extents arrive; responsive with 100k+ items). [flutter/flutter#52207](https://github.com/flutter/flutter/issues/52207) — knopp's & gnprice's comments.
- **`cacheExtent`** (Flutter ≥3.44: `scrollCacheExtent: ScrollCacheExtent.pixels(...)`): tune the offscreen build zone. Too small → items build mid-frame during fast scroll (jank); too large → wasted builds/memory. ~1 viewport is a good feed default; note the 3.44 deprecation/rename. [scroll-cache-extent breaking change](https://docs.flutter.dev/release/breaking-changes/scroll-cache-extent)
- **Keys**: stable key per item (event id) so Riverpod state, keep-alives, and scroll position survive prepends/reorders — same principle as Compose `key`. [Compose lazy lists docs](https://developer.android.com/develop/ui/compose/lists)
- **Avoid rebuild storms**: split widgets so only engagement counters rebuild (Riverpod `select`); `const` constructors everywhere; **don't** override `Widget.operator==` (O(N²)); avoid `Opacity` in items (use `AnimatedOpacity`/`FadeInImage`). [Flutter perf best practices](https://docs.flutter.dev/perf/best-practices)
- **RepaintBoundary**: wrap heavy items (media cards) to isolate repaints — but each boundary costs a layer; apply to media/video items, not every row. [Saropa RepaintBoundary guide](https://saropa.com/articles/why-flutters-repaintboundary-is-your-secret-weapon-against-jank)
- **AutomaticKeepAlive costs**: keeping items alive defeats viewport GC — memory grows with scroll depth. Prefer *not* keeping feed items alive; instead make rebuilds cheap (cached parsed text, cached counts). Amethyst's equivalent: content-addressed `CachedRichTextParser` so scroll-time composition is a cache hit. [Amethyst PR #3325](https://github.com/vitorpamplona/amethyst/pull/3325), [AutomaticKeepAlive docs](https://api.flutter.dev/flutter/widgets/AutomaticKeepAlive-class.html)
- **Amethyst's concrete playbook for Compose, translatable 1:1 to Flutter**:
  1. **Prefetch ahead of viewport off the main thread**: for the next/prev few notes — pre-parse rich text into the render cache (content-addressed, LRU 500), prefetch images into the image lib, **record decoded aspect ratios in a cache so the box is reserved on first layout → no layout jump**, warm link previews. Measured A/B: median and p90 frame times identical with prefetch on — pure win. [Amethyst PR #3325](https://github.com/vitorpamplona/amethyst/pull/3325)
  2. `remember()` flows to avoid re-subscribing per recomposition; `distinctUntilChanged()` so observers fire only on real change; sample/throttle chatty flows (500ms); shared 30s "now" ticker for time-ago labels instead of per-item timers; coroutine per item only for items that actually need it. [Amethyst PR #2857](https://github.com/vitorpamplona/amethyst/pull/2857)
  3. LazyColumn `key` + `contentType` for item reuse. [Compose lazy layouts performance](https://developer.android.com/agents/skills/jetpack-compose/jetpack-compose-performance/references/lazy-layouts)

### 2.2 Image loading strategy

- **Flutter's built-in memory cache**: `PaintingBinding.imageCache` = LRU, **1000 images / 100 MB default**. Fast scrolling can evict images you're about to re-show; tune `maximumSize`/`maximumSizeBytes` deliberately, or the inverse — *shrink* it on low-end Android. [ImageCache API](https://api.flutter.dev/flutter/painting/ImageCache-class.html), [redlinesoft caching guide](https://blog.redlinesoft.net/posts/flutter-image-loading-caching)
- **Decode at display size — the single biggest memory win**: `cacheWidth`/`cacheHeight` (`Image.network`) or `memCacheWidth`/`memCacheHeight` (CachedNetworkImage), computed as `displayLogicalPx × devicePixelRatio`. A 4000×3000 photo decoded full-res is ~48MB; decoded at 360dp it's ~1MB. This directly fixes "fine at first, janky/OOM after scrolling a while." [Ximya's guide](https://medium.com/make-android/save-your-memory-usage-by-optimizing-network-image-in-flutter-cbc9f8af47cd), [Saropa image optimization](https://saropa.com/articles/how-we-reduced-flutter-memory-usage-by-375mb-image-optimization-strategies), [flutter#56239 caveat: cacheWidth is physical px](https://github.com/flutter/flutter/issues/56239)
- **Downsample at the source when you can**: Nostrudel's `IMAGE_PROXY` pattern (imageproxy server resizes profile images) — i.e., CDN resize params. Amethyst prefetches NIP-92 imeta and reserves boxes by aspect ratio. [nostrudel repo](https://github.com/hzrd149/nostrudel), [Amethyst PR #3325](https://github.com/vitorpamplona/amethyst/pull/3325)
- **Placeholders**: blurhash (Amethyst ships a blurhash composable + hydration preloader; NostrFeed web already has the pattern). Fade-in ≤150–300ms; reserve fixed-height containers so rows don't jump. [redlinesoft guide](https://blog.redlinesoft.net/posts/flutter-image-loading-caching)
- **Disk cache**: `cached_network_image` uses flutter_cache_manager (default: 200 objects, 30 days — bounded, unlike memory). Consider a custom CacheManager with explicit limits, and stable `cacheKey`s (signed URLs poison cache keys). [cached_network_image#429](https://github.com/Baseflow/flutter_cached_network_image/issues/429), [ASOasis caching strategy](https://asoasis.tech/articles/2026-09-12-0853-flutter-network-image-caching-strategy)
- **Prefetch**: `precacheImage()` for the next few feed items (offscreen) — Flutter equivalent of Amethyst's Coil warm.

### 2.3 Preventing "scroll stuck after some time"

Root causes, in order of likelihood for this stack:
1. **Image memory growth** → GC pressure / jank: full-res decodes + 100MB mem cache + 500+ images = >1GB RSS. Confirmed pattern in community reports ("150 images then crash", "above 1GB"). Fix = §2.2 downsampling + bounded cache. [reddit memory problems thread](https://www.reddit.com/r/FlutterDev/comments/eqvvpv/memory_problems_for_long_listviews_with_image)
2. **Leaked controllers/subscriptions**: undisposed `ScrollController`, `StreamSubscription` (websocket events!), video controllers accumulate → "minor leaks accumulate and lead to noticeable performance declines over time" in long-running social apps. Dispose diligently; Riverpod `autoDispose` for feed providers; cancel relay subs when feed leaves (the WhileSubscribed(5000) pattern). [DCM memory leaks](https://dcm.dev/blog/2024/10/21/lets-talk-about-memory-leaks-in-dart-and-flutter)
3. **Video**: don't prefetch video bytes (Amethyst deliberately doesn't — "large, often HLS; the player pool already starts fast — the poster covers the visible card"); pool players, dispose offscreen controllers, show poster frame. [Amethyst PR #3325](https://github.com/vitorpamplona/amethyst/pull/3325)
4. **Unbounded in-memory model growth**: mirror Amethyst's NIP-40 sweep — periodic DELETE of expired + old non-referenced events from sqflite; cap the in-memory feed window (keep N pages, trim tail — Twitter windowing: "off-screen elements are recycled or unmounted to minimize memory usage"). [quartz README](https://laantungir.net/git/laantungir/amethyst/src/branch/main/quartz), [systemdesign.one Twitter deep dive](https://newsletter.systemdesign.one/p/system-design-interview-twitter)
5. **Leak detection**: Flutter DevTools Memory view (heap snapshots, allocation tracking) on a long scroll session; `debugPrint` image cache size periodically (`PaintingBinding.instance.imageCache.currentSizeBytes`). [DevTools memory](https://docs.flutter.dev/tools/devtools/memory)
6. Profile in **profile mode**, never debug. Use Impeller (default now) to kill first-run shader jank. [Flutter rendering performance](https://docs.flutter.dev/perf/rendering-performance)

## 3. BACKGROUND PROCESSING

- **Android Doze kills naive persistent sockets**: Doze defers network/jobs/alarms; foreground services are exempt, but Google explicitly says **use FCM rather than maintaining your own persistent connection** for messaging. [Android Doze docs](https://developer.android.com/training/monitoring-device-state/doze-standby). Real-world data: ntfy measured ~5%/hour battery drain on 4G with a persistent WebSocket vs negligible for periodic-check apps (Element) and FCM apps. [ntfy#687](https://github.com/binwiederhier/ntfy/issues/687)
- **What Nostr clients do instead**:
  - **Amethyst**: connections never closed *while the app is in use*; relays reconnect adaptively; subs auto-restore after reconnect; 1000+ relay connections on mobile "without noticeable battery or bandwidth cost" (websocket frames are tiny; the cost is when the OS suspends you). [Amethyst README](https://github.com/vitorpamplona/amethyst), [OpenSats Amethyst](https://opensats.org/projects/amethyst)
  - **rx-nostr**: lazy connect (defer until needed), idle disconnect (temporarily drop unused connections), exponential-backoff + jitter reconnection (≤5 tries default), REQ re-issue on reconnect — with **lazy since/until** so re-issued filters re-evaluate timestamps instead of double-fetching a stale window. [rx-nostr README](https://github.com/penpenpng/rx-nostr/), [reconnection docs](https://penpenpng.github.io/rx-nostr/en/v3/reconnection.html)
  - **EOSE discipline**: backward subs close on EOSE; aggregate per-relay EOSE into one "loading done" boolean so UI doesn't flicker (Amethyst `eoseManagers/`). [relay-client SKILL.md](https://laantungir.net/git/laantungir/amethyst/raw/tag/v1.13.1/.claude/skills/relay-client/SKILL.md)
- **Notifications without killing battery**: Nostr UX guidance — client polling, a **push-notification relay**, NIP-46 signer forwarding, or UnifiedPush; batch low-priority alerts (reactions batched; replies/mentions/zaps immediate). [nostr-ux.com content discovery](https://nostr-ux.com/docs/patterns/02-content-discovery). For this Flutter app: keep the websocket listener only in foreground; in background use `flutter_local_notifications` + periodic WorkManager sync (respecting Doze) or UnifiedPush — not a 24/7 socket.
- **Avoid duplicate work on reconnect**: dedup at ingest (event.id PK + INSERT OR IGNORE into sqflite — your `uniq()`), record `seen_on` (your `tie()`), and keep `since` cursors per feed so a reconnect resumes the live tail instead of re-fetching pages.

## 4. PRACTICAL CHECKLIST (prioritized, 14 items)

1. **Decode images at display size** (`memCacheWidth/Height` = logical px × devicePixelRatio) on every feed image/avatar — kills the #1 memory-growth jank source. [Ximya](https://medium.com/make-android/save-your-memory-usage-by-optimizing-network-image-in-flutter-cbc9f8af47cd), [Saropa](https://saropa.com/articles/how-we-reduced-flutter-memory-usage-by-375mb-image-optimization-strategies)
2. **Serve the feed from sqflite, not from the relay stream**: ingest → validate → `INSERT OR IGNORE` → UI queries local DB (Damus local-relay model). Removes rogue data, parse-on-render, and double processing. [Damus #2041](https://github.com/damus-io/damus/issues/2041)
3. **Normalize schema with a tag-index table** (`event_tags(tag_name, tag_value, event_id)`) + precomputed `engagement` table refreshed on ingest — renders become dumb SELECTs (Primal pre-computation principle, client-side). [Primal server](https://github.com/PrimalHQ/primal-server)
4. **Intern events in memory** (one object per id) with an interning layer between sqflite and Riverpod — single source of truth, engagement updates propagate without re-querying (Amethyst InterningEventStore). [quartz](https://laantungir.net/git/laantungir/amethyst/src/branch/main/quartz)
5. **Batch all secondary fetches**: collect visible notes → one REQ for kind:0 of all missing pubkeys, one for kind:7/kind:1 `#e` engagement — via a 500–1000ms debounce buffer + merge (rx-nostr `bufferTime+batch`; Amethyst FeedMetadataCoordinator). [rx-nostr operators](https://penpenpng.github.io/rx-nostr/en/v3/req-packet-operators.html)
6. **Backward = `until` cursor pages that close on EOSE; Forward = one live-tail sub with lazy `since`** re-evaluated on reconnect — stable pagination, no dupes, no re-fetch on reconnect. [rx-nostr subscribe/reconnection](https://penpenpng.github.io/rx-nostr/en/v3/reconnection.html)
7. **Live tail inserts above a "N new notes" pill; never splice into the visible window** — preserves scroll position and item keys (Primal/Twitter pattern). [primal-shim](https://github.com/sovITxyz/nostr-swarm/blob/main/docs/primal-shim.md)
8. **Stable keys = event id** on feed items; `const` item widgets; Riverpod `select` for per-item engagement so a zap only rebuilds one counter. [Flutter perf](https://docs.flutter.dev/perf/best-practices), [Amethyst #2857](https://github.com/vitorpamplona/amethyst/pull/2857)
9. **Prefetch ±5 items ahead off the UI thread**: `precacheImage` + pre-parse rich text into a content-addressed LRU (~500) + cache decoded aspect ratios to reserve layout boxes → zero-jump scroll. Amethyst measured no main-thread cost. [Amethyst #3325](https://github.com/vitorpamplona/amethyst/pull/3325)
10. **Cap the in-memory feed window and sweep the DB** (trim loaded pages; periodic DELETE of expired/old events, NIP-40 sweep every ~15 min) — bounds memory growth over long sessions. [quartz AppGraph](https://laantungir.net/git/laantungir/amethyst/src/branch/main/quartz), [Twitter windowing](https://newsletter.systemdesign.one/p/system-design-interview-twitter)
11. **Parse NIP-10 once per event at ingest** (root/reply/mentions incl. legacy positional) and persist pointers — threads assemble from local store; backfill missing parents via relay hints/author write relays on demand. [NIP-10](https://github.com/nostr-protocol/nips/blob/master/10.md), [applesauce threading](https://github.com/hzrd149/applesauce/blob/e5a93dc9e8d621137590845e139926638e954312/packages/common/src/helpers/threading.ts)
12. **Record `seen_on(event_id, relay_url)`** for every event — powers relay hints for thread backfill, outbox routing, and per-relay health scoring. [rx-nostr tie()](https://penpenpng.github.io/rx-nostr/en/v3/event-packet-operators.html)
13. **Aggregate EOSE per feed into one "loaded" flag**; reference-count shared subscriptions so navigating between screens never opens duplicate subs. [Amethyst relay-client skill](https://laantungir.net/git/laantungir/amethyst/raw/tag/v1.13.1/.claude/skills/relay-client/SKILL.md)
14. **Background = periodic sync + local notifications, not a 24/7 socket**: foreground-only websockets; WorkManager periodic catch-up; UnifiedPush/notification relay later. Doze will throttle a persistent socket anyway, and 4G sockets measurably drain ~5%/hr. [Android Doze](https://developer.android.com/training/monitoring-device-state/doze-standby), [ntfy#687](https://github.com/binwiederhier/ntfy/issues/687)
